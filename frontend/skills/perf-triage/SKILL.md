# 프론트엔드 성능 트리아지

코드에서 원인을 먼저 고르지 않는다. 사용자가 느끼는 증상을 고정하고 같은 조건의
수정 전후 측정으로 결론을 낸다.

## 진행

1. 느린 경로, 입력, 화면 크기, 네트워크 조건과 기대 동작을 확인한다. 재현 경로를
   하나로 줄이고 개발 모드와 프로덕션 빌드를 구분한다.
2. 레포에 이미 있는 브라우저 자동화, 성능 기록, 번들 분석 명령을 먼저 찾는다.
   새 도구를 추가해야 하면 비용과 이유를 설명하고 작업 범위 안에서만 추가한다.
3. 변경 전 기준값을 남긴다. 문제에 맞춰 탐색 시작, 핵심 리소스, 긴 태스크,
   상호작용 지연, 레이아웃 이동, 렌더 횟수, 전송량 중 필요한 것만 잰다.
4. 트레이스, 네트워크 워터폴, 프로파일 또는 번들 결과가 가리키는 병목을 코드의
   소유 지점까지 연결한다. 관찰과 추론을 구분한다.
5. 병목 하나를 겨냥한 최소 변경을 하고 같은 시나리오와 조건으로 다시 잰다.
   기능 회귀도 함께 확인한다.

## 완료 기준

- 재현 조건과 측정 수단이 적혀 있다.
- 수정 전후의 같은 지표가 비교된다.
- 개선과 남은 병목, 측정의 한계를 구분해 보고한다.
- 측정할 수 없으면 원인을 단정하지 않고 필요한 계측이나 재현 조건을 남긴다.
