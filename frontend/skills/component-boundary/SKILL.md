# 컴포넌트 경계 결정

줄 수가 아니라 변경 이유와 상태 소유권으로 경계를 정한다. 추상화 개수보다 이후
변경이 한 소유자에서 끝나는지가 중요하다.

## 판단 순서

1. 사용자 동작과 화면 상태를 적고, 어떤 상태들이 함께 변해야 하는지 찾는다.
2. 상태는 그것을 함께 읽고 쓰는 가장 가까운 공통 소유자에 둔다. URL, 서버 상태,
   여러 화면의 동기화가 이유일 때만 더 위로 올린다.
3. 독립적인 변경 이유, 재사용되는 계약, 별도 로딩·오류 경계, 독립 검증 가치가
   있을 때 컴포넌트를 나눈다. 파일 길이 하나만으로 나누지 않는다.
4. 데이터 변환과 부수 효과는 그 결과와 수명 주기를 소유하는 경계에 둔다. 같은
   원본 상태의 복제, 동기화용 효과, 전달만 하는 래퍼가 늘면 소유 위치를 다시 본다.
5. 프레임워크가 서버와 클라이언트 경계를 구분하면 상호작용이 필요한 최소 표면만
   클라이언트에 두고, 경계를 넘는 값은 직렬화 가능한 계약으로 유지한다.

전역 상태나 컨텍스트는 깊은 전달 자체가 아니라 여러 독립 소비자가 같은 수명
주기의 상태를 공유해야 할 때 선택한다. 한 번만 쓰는 추상 컴포넌트는 예상 재사용을
근거로 만들지 않는다.

## 검증

분리 뒤에도 사용자 동작, 로딩, 오류, 포커스와 상태 보존이 같아야 한다. 테스트는
내부 컴포넌트 트리보다 경계의 입력과 관찰 가능한 동작을 고정한다. 결과에는 선택한
소유자와 대안을 버린 이유를 짧게 남긴다.
