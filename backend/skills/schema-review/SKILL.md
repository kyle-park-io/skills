# 마이그레이션 사전 점검

## 언제 쓰나

- 마이그레이션 파일을 쓰기 시작할 때
- 남이 쓴 마이그레이션을 프로덕션에 적용하기 전
- 스키마를 바꾸는 PR 을 리뷰할 때

## 핵심 원칙

**마이그레이션은 앞으로만 가는 코드가 아니라 되돌아올 수 있는 코드다.** 롤백 경로를 문장으로 못 쓰면 아직 적용할 준비가 안 된 것이다.

그리고 배포 중에는 **구버전 코드와 신버전 스키마가 반드시 같이 존재하는 순간**이 있다. 이 순간에 깨지지 않는 것이 조건이다.

## 절차

### 1. 현재 스키마를 추측하지 않고 읽는다

컬럼명, 타입, 인덱스, 제약, 외래키를 실제 스키마에서 확인한다. 마이그레이션 히스토리나 ORM 모델 파일이 아니라 살아 있는 스키마를 본다. 둘이 갈라져 있는 경우가 이 단계에서 잡힌다.

행 수도 같이 확인한다. 아래 판단이 전부 규모에 따라 갈린다.

### 2. 이 변경이 파괴적인지 분류한다

| 종류 | 예 | 배포 중 안전한가 |
|---|---|---|
| 순수 추가 | nullable 컬럼, 새 테이블 | 안전 |
| 축소 | 컬럼·테이블 삭제, 타입 축소 | 구버전 코드가 깨진다 |
| 이름 변경 | 컬럼·테이블 rename | 구버전 코드가 깨진다 |
| 제약 강화 | NOT NULL, UNIQUE, 외래키 추가 | 기존 데이터가 위반하면 실패한다 |

축소와 이름 변경은 **한 번에 하지 않는다.** 확장 후 축소로 쪼갠다.

1. 새 컬럼을 nullable 로 추가한다
2. 양쪽에 함께 쓰도록 코드를 배포한다
3. 기존 행을 백필한다
4. 읽기를 새 컬럼으로 옮겨 배포한다
5. 옛 컬럼을 지운다

각 단계 사이에 배포가 한 번씩 들어간다. 한 PR 에 다 넣으면 쪼갠 의미가 없다.

### 3. 락이 얼마나 걸리는지 따진다

큰 테이블에서 테이블 전체 락을 잡는 작업은 서비스를 세운다. 최소한 이건 확인한다.

- 인덱스 생성이 쓰기를 막는가. Postgres 면 `CONCURRENTLY`, MySQL 이면 온라인 DDL 조건을 확인한다
- 기본값이 있는 컬럼 추가가 테이블을 다시 쓰는가. DB 버전마다 다르다
- 제약 추가가 전체 스캔을 하는가. 검증을 분리할 수 있으면 분리한다
- 백필을 한 트랜잭션에 넣지 않는다. 배치로 쪼개고 중단·재개가 되게 한다

### 4. 롤백 경로를 문장으로 쓴다

"이 마이그레이션을 되돌리려면 무엇을 하는가"를 한 문단으로 쓴다. 되돌릴 수 없는 변경이면 그렇다고 명시한다.

되돌릴 수 없는 것들이다.

- 데이터를 지우는 변경. 삭제 전에 어디에 남는지 적는다
- 정보를 잃는 타입 변경. `text` 에서 `varchar(50)` 같은 것
- 백필로 덮어쓴 원본 값

되돌릴 수 없으면 적용 전 백업 지점을 정하고, 어디까지 되돌릴 수 있는지 적는다.

### 5. 배포 순서를 정한다

스키마와 코드는 동시에 배포되지 않는다. 어느 쪽이 먼저인지 정하고, 그 사이 기간에 양쪽이 다 도는지 확인한다.

- 스키마 먼저: 순수 추가일 때
- 코드 먼저: 새 컬럼 쓰기를 준비시킬 때
- 지우기는 항상 마지막. 구버전 코드가 전부 내려간 뒤

### 6. 위반 데이터를 미리 센다

제약을 추가하기 전에 위반하는 행을 세는 쿼리를 먼저 돌린다. 0 이 아니면 마이그레이션이 아니라 데이터 정리가 먼저다.

## 하지 말 것

- 스키마를 안 읽고 컬럼명을 추측하지 않는다
- 삭제와 추가를 한 마이그레이션에 같이 넣지 않는다
- 백필을 마이그레이션 안에서 한 트랜잭션으로 돌리지 않는다
- "롤백은 그냥 반대로 하면 된다"로 넘기지 않는다. 데이터가 있으면 대칭이 아니다
- 스테이징에서만 확인하고 넘어가지 않는다. 락 문제는 데이터 규모에서만 드러난다

## 검증

적용 전에 이 다섯 개에 답이 나와야 한다.

1. 실제 스키마를 읽었는가. 대상 테이블의 행 수는 얼마인가
2. 배포 중 구버전 코드가 이 스키마에서 도는가
3. 최대 락 시간은 얼마인가
4. 롤백 절차가 한 문단으로 쓰여 있는가. 못 되돌리면 명시했는가
5. 제약을 추가한다면 위반 행 수가 0 인가
